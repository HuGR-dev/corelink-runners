# action-archive-pins.txt — actions pre-seeded into the runner's read-only
# action-archive cache (ACTIONS_RUNNER_ACTION_ARCHIVE_CACHE), baked by the
# Dockerfile's action-cache-download stage.
#
# WHY: all self-hosted runners egress through one IP; a broad corelink-server PR
# fans ~20 gates out at once, each cold-downloading actions/checkout (+friends)
# from codeload.github.com. Concurrent downloads on one IP trip codeload's
# per-IP rate limit (429 Too Many Requests), failing jobs at "Set up job" with
# no test run. Baking these tarballs makes every ephemeral runner start warm:
# the runner (>=2.335) finds the archive locally and never hits codeload.
#
# INTEGRITY: the 40-hex is a git COMMIT SHA — itself a cryptographic hash of the
# action's tree — so pinning by SHA IS the supply-chain anchor (X4 floor). A
# separate tarball sha256 is deliberately NOT pinned: git-archive tarballs are
# not byte-reproducible across git versions, so such a pin would be brittle and
# add no integrity over the commit SHA. The build fetches by that SHA.
#
# SCOPE: the high-frequency actions that drive the per-PR download burst on
# HuGR-Labs/corelink-server (counts as of 2026-08-17). This is the SAME
# "bake what corelink-server actually asks for" discipline as the node/pnpm
# pins. To REFRESH after a dependabot pin bump, update the SHA here to match the
# new pin in corelink-server's .github/workflows/ (a stale entry just means one
# cold download for the new SHA until the image is rebuilt — self-limiting, not
# a failure).
#
# Format: <owner>/<repo>@<40-hex-commit-sha>   (blank lines + # comments ignored)
